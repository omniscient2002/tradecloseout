## Gateway deployment contract

API production/staging now also requires `AUTH_DELIVERY_CALLBACK_KEY` (at least 32 characters), HTTPS `DLT_SMS_STATUS_URL` and `MAIL_STATUS_URL`, and SMS/mail gateway credentials. The worker validates the status endpoints/credentials before scheduling; callback verification belongs to the API. Provision/rotate secrets through the deployment secret store, never repository files.

Submission requests include `deliveryAttemptId` and `idempotencyKey` with the same opaque UUID, `Idempotency-Key` and `X-Auth-Delivery-Contract: 1`. A successful bounded JSON acknowledgement must contain `accepted: true`, the exact `deliveryAttemptId`, and a 1–128 character `messageId` matching `[A-Za-z0-9._:-]+`. HTTP acceptance is submission evidence only. A callback may arrive before the acknowledgement; late or duplicate status must not revive a consumed or revoked target.

`POST /api/v1/auth/delivery/receipts` is authenticated independently of cookies using `X-Auth-Delivery-Timestamp` (Unix seconds within five minutes) and `X-Auth-Delivery-Signature` (hex HMAC-SHA256 over `timestamp + "." + exact raw body`, using the callback key). The JSON object has exactly `eventId`, `deliveryAttemptId`, `messageId`, positive safe-integer `sequence`, and `status` (`SUBMITTED`, `DELIVERED` or `FAILED`). Matching duplicate events return 204 without another transition. Conflicting/unknown events reject. Bodies and gateway JSON reads are bounded to 4096 bytes.

Status queries POST only `{deliveryAttemptId, idempotencyKey}` with the configured gateway bearer credential. A trusted status response uses the same receipt object. Retries are bounded and lease/backoff protected in PostgreSQL; no raw destination, OTP or invitation link is queued for replay. Expiry, ordering and terminal failures prevent revival. Real provider-specific event ordering, idempotency guarantees, signing/key rotation, delivery/bounce semantics, quotas and outage behavior must be independently demonstrated before enabling this contract with a vendor.

## Proposed supervised recovery operations

Migration 0039 creates NOLOGIN roles `tc_identity_recovery_reviewer` and `tc_identity_recovery_executor` and grants neither to runtime, migration, deployment or external-signatory identities. Provision individually accountable human LOGINs only after independent security/IAM approval. Database principals must not represent the claimant or share credentials; the database distinguishes logins, not real people. Human identity/delegation evidence and conflicts must be verified outside the application. Role separation is enforced by SQL even if an operator bypasses the CLI.

Use `pnpm --filter @tradecloseout/api review:identity-recovery --` with `G01_RECOVERY_DATABASE_URL` and `G01_RECOVERY_CA_PATH`. The URL must be a named, restricted human login distinct from app/migrator credentials. TLS CA verification is required. The CLI emits only case status metadata and fixed failure diagnostics.

1. Reviewer A uses `--action open --user <uuid> --sha256 <evidence-digest> --case <opaque-ref>` with `--attest-independent-identity --attest-no-self-review --attest-destination`. An optional `--new-contact-type EMAIL|PHONE --new-contact <verified-contact>` proposes a replacement. References/digests identify separately protected evidence; do not put secrets in case references or shell history. Opening revokes existing sessions but preserves factors and does not suspend all future authentication.
2. Reviewer B independently verifies the same evidence, target account and proposed destination, then uses `--action attest --id <case-uuid>` with the exact same user/digest/reference/contact/attestation arguments. Duplicate reviewer identity or substituted evidence is rejected. A reviewer may cancel with `--action cancel --id <case-uuid>`.
3. The worker sends security notices to existing verified contacts and, for replacement, the new independently verified destination. Old-contact notices require a provider-confirmed submission/failure status followed by a full 24-hour window; a contact replacement additionally requires a delivered receipt for the new destination. Gateway delivery does not independently prove human possession: both reviewers must verify that separately.
4. A distinct executor inspects with `--action inspect --id <case-uuid>` and checks the restricted case record and real notification evidence. It may use `--action execute --id <case-uuid> --attest-reviewed-policy --attest-notifications-checked` only after APPROVED state, minimum 24-hour case cooldown, old-contact notification window and new-contact delivery gates. Cases expire after 72 hours. There is no production cooldown override. Execution atomically changes the proposed contact if applicable, clears factors/recovery codes, revokes sessions, advances the old-proof fence and records an event. The user must authenticate afresh and re-enroll MFA.

The 24/72-hour values, accepted identity evidence, conflict rules, unreachable-old-contact handling, escalation/cancellation and post-recovery communication are **proposed policy requiring independent owner/security approval**. Do not provision these roles or treat this as an accepted operational recovery service before that approval. This implementation provides no automatic channel fallback or public support bypass.
