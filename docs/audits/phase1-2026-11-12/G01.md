## Findings and required corrections

### PH1-G01-001 — P1 / REPRODUCED: Generic idempotency storage defeats MFA secret-at-rest protection

**Source:** [apps/api/src/common/interceptors/idempotency.interceptor.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/common/interceptors/idempotency.interceptor.ts), [apps/api/src/modules/identity/mfa.controller.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/modules/identity/mfa.controller.ts).

**Observation and limits:** The actual MFA enroll/start controller, wrapped by the actual idempotency interceptor, writes its returned manualSetupKey in plaintext to idempotency_keys.response_json. The browser adds Idempotency-Key to POSTs. Confirmation also returns recovery codes, so every secret-bearing response needs review.

**Required correction:** Exclude secret-bearing auth responses from generic receipt capture or design a dedicated encrypted, actor/session-bound, tightly expired one-time result contract. Inventory and securely expire existing plaintext receipts without weakening forensic obligations. Do not merely redact the response sent to the legitimate user.

**Acceptance:** Exercise enrollment, confirmation, recovery, rotation and retries through the actual interceptor/HTTP stack; database dumps, logs, outbox and receipts contain no plaintext factor/recovery/session credentials. Lost-response behavior remains safe.

**Executed local observations:** P21. See the evidence JSON; a reproduction passing is not a repaired control.

### PH1-G01-002 — P1 / REPRODUCED: Expiry of a previous encryption key disables valid current-key MFA

**Source:** [apps/api/src/modules/identity/mfa-crypto.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/modules/identity/mfa-crypto.ts), [apps/api/src/modules/identity/auth-security.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/modules/identity/auth-security.ts).

**Observation and limits:** decryptFactor constructs previousEncryptionKey before trying the current key. Once the configured previous-key deadline expires it throws, even for an envelope encrypted with the current key. Current recovery-code candidate lookup similarly fails.

**Required correction:** Continue validating/decrypting current-key material after the previous-key window closes; reject only expired previous-key material. Define key IDs, re-encryption progress, emergency rotation and removal of retired configuration. Preserve expiry rather than extending old-key acceptance indefinitely.

**Acceptance:** Use a controlled clock across the retirement boundary: current factors/codes work, old unconsumed material follows the approved expiry policy, replay stays blocked, and key logs/metrics reveal no secret.

**Executed local observations:** P19, P20. See the evidence JSON; a reproduction passing is not a repaired control.

### PH1-G01-003 — P2 / SOURCE_CONFIRMED: Pending MFA enrollment lacks an explicit expiry/session-bound proposal

**Source:** [apps/api/src/modules/identity/mfa.controller.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/modules/identity/mfa.controller.ts), [apps/api/src/modules/identity/mfa-crypto.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/modules/identity/mfa-crypto.ts).

**Observation and limits:** Enrollment stores a pending encrypted secret on the user and confirmation later consumes it; there is no pending-factor expiry or enrollment proposal/session identity in the inspected contract. Account/session locking is present and must be preserved.

**Required correction:** Bind setup to a single expiring proposal and current authenticated session/generation, invalidate older proposals on restart/recovery and define safe notification of factor changes. Do not allow an indefinite pending setup to become an unreviewed recovery path.

**Acceptance:** Expired, replaced, cross-session and cancelled proposals deny; valid setup succeeds once; concurrent starts/confirms serialize and do not overwrite or disclose another proposal.

### PH1-G01-004 — P1 / REPRODUCED: Session freshness must include live eligibility inside protected work

**Source:** [apps/api/src/common/guards/session-csrf.guard.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/common/guards/session-csrf.guard.ts), [packages/db/src/tenant-tx.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/packages/db/src/tenant-tx.ts), [apps/api/src/database/tenant-db.service.ts](https://github.com/omniscient2002/tradecloseout/blob/9ed91a9e96c77c9eff967f6c845d18c38fb62ac6/apps/api/src/database/tenant-db.service.ts).

**Observation and limits:** The newer guard implements generation, idle/absolute expiry, MFA and current membership checks. The later transaction fence still accepts a valid session after an organisation-state change and bypasses live project authority for a stale Owner snapshot. This overlaps PH1-G26-004 and should have one shared correction.

**Required correction:** Make authentication and transaction-authority contracts agree on account/member/org suspension and the linearization point. Preserve emergency logout/revocation and authorised selection of another organisation; tenant suspension must not masquerade as ordinary credential expiry.

**Acceptance:** Real HTTP commands across two instances, suspended current org plus eligible alternate org, concurrent account/membership suspension, delayed requests and offline retries obey the documented policy.

**Executed local observations:** P13, P14. See the evidence JSON; a reproduction passing is not a repaired control.

## What must be achieved before production

1. Original G01-001..021 obligations are individually reconciled and independently accepted at the exact final candidate; no status is inherited from old reviews.
2. No plaintext OTP/factor/recovery/session credentials survive any generic receipt, audit, outbox, log, cache, trace or dump path.
3. Current/retired key rotation, OTP single-use, MFA replay, expiring enrollment and lost-response/device/factor/destination behavior pass real integration tests.
4. Actual production-mode API and browser behind HTTPS/proxy enforce origin/intent/CSRF, Secure cookie, MFA and generation/idle/absolute/session revocation policy.
5. Two actual API replicas plus shared stores pass crash/response-loss/replay/budget/spoofing/suspension and offline/in-flight fencing drills.
6. Real DLT/SMS/email provider receipts, ordering, timeout, bounce, quota/spend and reconciliation evidence is reviewed.
7. Independently established external contact/legal authority and distinct reviewer/executor IAM/recovery policy are approved and tested.
8. Security events, privacy/retention, cache/referrer inspection, SIEM alerts and incident/secret recovery drills pass on the deployed release.
