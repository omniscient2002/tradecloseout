# HVAC publication and external acceptance

No independently approved HVAC catalogue/pack has been supplied for this candidate. `HVAC_DOMAIN_APPROVAL` remains **BLOCKED_EXTERNAL**. Migration0053 seeds no pack, reviewer identity, membership or approval. Existing ACTIVE rows retain their original facts and cannot pass the reviewed-pack gate retrospectively. Existing catalogue identifiers and contractual obligations are unchanged.

The database creates NOLOGIN author/reviewer groups. A responsible operator must separately provision accountable least-privileged human database identities after verifying authority and reviewer qualification. The application runtime has only template SELECT; it cannot insert/update/delete/truncate, attach triggers or execute publication commands. Do not grant publication groups to tc_app. Reviewer qualification and evidence must be verified by the accountable release reviewer; SQL syntax checks cannot establish engineering correctness.

Use `pnpm exec tsx scripts/hvac-template-governance.ts --help`. Configure `HVAC_GOVERNANCE_DATABASE_URL` through the operator's secret configuration for the relevant human identity. There is no application/admin URL fallback; superuser, bypass-RLS and ordinary application identities are refused. Do not put connection strings in files, command arguments or review records.

1. `stage FILE.json`: input contains packId(UUID), code, name, integer version and payload. Payload uses schema1 requirements with explicit existing document identifiers, titles, group, boolean mandatory and PROJECT/ASSET_CATEGORY scope. A shared pack cannot contain tenant asset UUIDs. Supported groups/sections must also have stable unique keys. Publication performs bounded syntax/structure validation; it does not infer engineering obligations or fix mappings on the author's behalf. Corrections require a new immutable version.
2. `inspect PACK_UUID`: read the exact stored definition/checksum and provenance before deciding. Verify identifiers, catalogue mappings, applicability, companion rules, representative project scenarios and contractual obligations independently. Legacy catalogue examples and rules are references, not approval evidence.
3. `review FILE.json`: input contains packId and reviewRecord. The separately provisioned reviewer must differ from the actual staging database identity. reviewRecord requires candidateSha(full40-character commit SHA), qualifiedReviewerEvidence, catalogueRef, mappingEvidence, applicabilityEvidence, scenarioEvidence and an explicit exceptions array(empty only when there are no exceptions). References must be durable HTTPS record URLs without credentials or query tokens. Review stores actual session identity and database approval timestamp; it cannot be supplied as a forged requester string. Replaying an identical decision is idempotent. Published payload and review identity/evidence cannot be rewritten.
4. `deprecate FILE.json`: input contains packId and an attributable reason. Retirement prevents new installation. Previously installed project snapshots retain their immutable definition; this does not silently change a contract or revive an old version.

Only genuinely supplied evidence can satisfy the required review fields. Test files use distinct **synthetic** database identities and example.invalid references in disposable databases to exercise role/state mechanics. They do not designate a real pack independently approved and cannot close the release gate.

Final release acceptance must record the exact final candidate SHA, immutable reviewed catalogue/pack versions, accountable qualified reviewer identity, approval date, real scenario/acceptance evidence and explicit exceptions. Reconcile those records with the candidate release register. The implementation agent cannot approve itself or replace external business acceptance with test results. No production publication or group provisioning is performed by this change.
