## Baseline and honest estimate

- **52 audit rows:** 25 `PARTIAL / VERIFY`, 20 `OPEN`, 7 `BLOCKED_EXTERNAL`; **0 independently closed**. Partial fixes and passing CI are not closure.
- **22 scoped engineering remediation passes** (01–22), followed by **4 integrated engineering verification/review passes** (23–26) = **26 planned passes for code-only release-candidate readiness**, excluding live integrations and external domain acceptance.
- **4 separately grouped external evidence/operational acceptance passes** (27–30), covering all **7 external gates**, are explicitly deferred until providers, real customer/OEM/finance approval and independent evidence are available.
- **30 planned passes end-to-end**; budget **5–10 extra rework passes** based on real integration failures, CI regressions, migration replay, and independent review. This is a pass estimate, **not a promised schedule or claim of eventual zero defects**. Code-only could require roughly **26–33**; full readiness with external acceptance roughly **30–40**.
- The number of passes **does not decrease** merely because a previous pass changed code; pass closure depends on the acceptance proof. All IDs are assigned exactly once as primary work; the integration passes revisit every applicable acceptance criterion.

## Non-negotiable exit checklist for every engineering pass

1. Capture the **specific outstanding subrequirements** from the original group audit; label old implemented items `PREVIOUSLY PARTIAL`, never `CLOSED` without verification.
2. Commit minimal coherent implementation on `fix/phase-4-fixes` with tagged PH4 IDs and no unrelated phase edits. Keep live providers **disabled**; use ports/contracts and deterministic fake adapters for provider-dependent code.
3. Add success, boundary, negative authorization, replay/concurrency and regression tests (real PostgreSQL/HTTP/browser where appropriate). For any schema change, prove fresh install **and** upgrade of legacy records; preserve accepted immutable evidence.
4. Record exact commit SHA, CI URL/status, changed files, DB/script outputs, reviewer link and residual risks in the acceptance matrix and PR. An in-progress or previously green CI does not certify the new HEAD.
5. Independent reviewer confirms each audit acceptance subrequirement. If blocked by missing approved HVAC/recipient/OEM/finance policy or real provider, mark `BLOCKED_EXTERNAL` or `PARTIAL / VERIFY`, not `CLOSED`.
6. Keep the PR **DRAFT**. Do not label production-ready while any P0/P1, audit row, evidence gate, provider dependency or security/recovery condition is unresolved.

## Dependency and execution notes

- **01–03** close the defect integrity/security spine before adding new customer-facing actions. **04–06** establish canonical technical evidence; **07–13** compile and archive it; **14–17** handle current package acceptance; **18–19** handle downstream warranty; **20–22** handle finance without issuing unsupported payments/tax claims. Local sequencing may change to resolve a prerequisite, but never silently drop an ID.
- **23–26 are mandatory** even if all feature passes have green CI: exact-head integration, long-running worker crash recovery, tenant-negative isolation, actual browsers, reversible migrations, deployment/backup rehearsal and independent code review.
- **27–30 are not executable from synthetic data alone.** Missing independently reviewed HVAC catalogue/procedures or billing/grace policy, live customer/OEM verification and provider credentials must remain explicit release gates rather than being fabricated.
- Code-only release-candidate readiness (`CODE_READY_PROVISIONAL`) is **not** unrestricted production readiness. A genuine production `GO` requires all 52 audit rows independently closed, all applicable external acceptance and safety gates met, and complete staged deployment/runbooks.
