## Reproduced defects and correction

On a real database migrated through the original 0045, restricted `tc_app` could
read two projects with conflicting tenant aliases. With only the user's context,
it could DELETE two own memberships across organisations. The latter occurred
because the self-discovery predicate belonged to an ALL policy; WITH CHECK does
not restrict DELETE. Both reproductions run inside rolled-back test transactions
before the actual forward upgrade, then the same attacks are rejected afterward.

Append-only migration 0046 replaces raw tenant-setting expressions in existing
policies with `public.current_app_org_id()`. It preserves policy commands, roles,
permissiveness and existing exceptions. Unknown raw expressions abort migration.
Both alias spellings remain supported, equal UUID values compare as UUIDs,
conflicting aliases fail closed, and invalid UUID errors do not echo their values.

A restrictive context-validation policy on every tenant relation prevents an OR
exception from bypassing alias validation. It grants no row access by itself.
Self-membership discovery becomes SELECT-only; writes need the active tenant.
Active, unexpired guest-token lookup remains SELECT-only, followed by explicit
tenant binding for writes. Invitations remain tenant-scoped, including in token
context; this does not invent a missing invitation acceptance flow. Existing
global catalogue reads and explicitly scoped organisation bootstrap remain usable.
The migrator-only future audit partition provisioner installs the same policies.

Historical table ownership is mixed between `tc_migrator` and the authenticated
migration administrator. The policy DDL uses that administrator's existing
ownership authority. This continues the privileged migration contract required by
0045; it does not transfer ownership, grant runtime rights, disable RLS or edit
applied SQL/checksums. The entire migration is in the migrator's transaction.
